# Staged official admission client

`src/official-admission.js` is an unwired prerequisite. It uses the existing staff-authenticated redemption route; it adds no route, anonymous authority, UI, activation, gameplay, configuration or production enablement. The server remains authoritative for ticket consumption, receipt identity, lifecycle and exactly three scored turns.

## Caller and recovery contract

1. On an explicit new-admission action, call `prepare(code)`. It generates independent UUIDv4 `requestKey` and `nonce`, binds them to the canonical ticket's SHA-256 fingerprint, and writes and reads back the complete intent in localStorage before returning. Refused writes, unavailable reads and silently dropped writes fail before networking. Browser storage is not a backup: later eviction or manual deletion cannot be recovered by inventing identifiers.
2. Call `redeem(requestKey, code)` with that intent and the original ticket. Every POST first persists and reads back its submitted marker and identifiers. The code is sent only in the JSON body of `/api/official/redeem`, with same-origin credentials and an eight-second deadline. No URL, logging, telemetry or durable plaintext ticket storage is used. Codes are case-normalized for fingerprint comparison to match the server. Request/nonce/fingerprint are not session credentials. The official capability stays in the server-issued HttpOnly cookie.
3. A lost response, parse failure, post-response storage failure or server rejection retains the same intent. Retry explicitly with the same key and ticket; never call `prepare` as a retry. The server replays that owner's receipt and capability without consuming another ticket. Retain the ticket outside this client until the receipt is safely stored. After reload, `list` and `read` recover metadata without network calls; re-entry of the original ticket is required to replay redemption. The original staff owner cookie and authorized staff session are still required. Lost owner credentials, missing ticket or expired capability require host help, not anonymous fallback or a fresh request key.
4. Successful redemption persists the receipt before returning it with the nonce. Only an intent prepared by this live client with an accepted receipt has `recoveryRequired: false`. The future integration must check that flag and explicitly pass the receipt/nonce to the official-session adapter for activation. All reconstructed clients report recovery-only, even for accepted receipts. Never activate automatically on reload or treat a stored receipt as permission to restart physics. Existing outboxes use their own `initialize`/drain/interruption protocol; unfinished attempts use host-owned recovery. This module neither calls activation nor creates the outbox's run/active markers.

Keep one live client responsible for an intent. Operations on that client reject overlapping work for the same key; separate intents have separate storage entries and never overwrite a shared array. Cross-tab coordination is not a new lock or authority system: an explicit retry from another page is recovery-only, and server transactions remain the single-consumption boundary. A capability may identify only one run; switching it does not authorize draining or deleting other attempts.

## Retention and cleanup

The separate `cloud-claw:admission:v1:<requestKey>` namespace retains only identifiers, ticket fingerprint, submitted marker and server receipt. It never edits official or legacy score outboxes. It does not retain the ticket secret in a closure after a call finishes. Callers must avoid logging input/returned data and dispose their own ticket input state.

`discard` removes only a never-submitted intent with no operation in flight. Once a POST may have happened, even a rejection does not prove that a previous response was not lost; the record is retained. `acknowledge` is an explicit cleanup action and reads the current official session. It removes admission metadata only if that capability identifies the stored receipt and the server reports complete, void or expired. Active, accepted, interrupted, mismatched and unavailable capabilities cannot clear it. Score outboxes require their own acknowledgements and are never cleared here.

There is no automatic expiry or broad storage reset. Uncertain/rejected intents without a retrievable receipt, or records whose capability can no longer be restored, stay for host adjudication; this slice provides no UI for deleting those unresolved records. Host recovery, logout/player handoff and any later reviewed local-data disposal must remain explicit. A new ticket is a new intent only after the host's decision; local deletion never voids a server run, refunds a ticket or grants another attempt.

Disposable HTTP/storage regressions cover refusal before consumption, lost response and reload with identical identifiers/cookie, receipt-write failure, ticket/intent isolation, integration with the official outbox's three turns, guarded cleanup and server rejection. No browser journey is added because no application entry point imports this module. Product UI, physical acceptance and production enablement remain separate work.
